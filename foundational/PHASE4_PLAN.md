# Phase 4 — Sharing & Real-Time

## Context

Phases 0–3 of EveryList (see `foundational/PLAN.md`) are complete: auth, list/item/category/store/favorite CRUD, and a themed app shell all work, but every permission check in the backend is still `.where('ownerId', user.id)` — a deliberate Phase-2 stopgap noted in the plan, since `ListMember`/sharing didn't exist yet. Phase 4 (§7/§8/§10/§14 of PLAN.md) closes that gap: it introduces real multi-user list membership with roles, a shareable join-link invite flow, and Adonis Transmit (SSE) so members see each other's edits live with a "list was modified" toast.

Scope decisions locked in with the user before this plan:
- **Invites are join-link/code only** in this pass — no SMTP2GO/email sending. A link is generated by an owner/editor, previewable pre-auth, accepted post-auth.
- **Full entity scope**: List, Category, Item, Favorite, Store, and StoreCategoryOrder all move from ownerId checks to membership/role checks and all broadcast SyncEvents.
- **Transmit, local in-process transport** (matches the single-instance deployment target — no Redis).
- **No `version` column / conflict resolution** — that's Phase 5 (offline sync). Phase 4's `SyncEvent` table exists only to drive SSE broadcasts.

## 1. Database (new migrations, in this order)

**`list_members`** — `id, list_id` (FK→lists, CASCADE), `user_id` (FK→users, CASCADE), `role` (`owner`|`editor`|`viewer`), `invited_at`, `accepted_at` (nullable), timestamps. Unique `(list_id, user_id)`.
Same migration's `up()` **backfills** one `owner` row per existing `List` (from `lists.owner_id`) — required so existing lists don't become invisible to their owners the moment controllers switch off `ownerId`.

**`list_invites`** — separate table from `list_members` (a link is reusable by multiple people and has its own revoke/expire lifecycle; keeping `list_members.user_id` always non-null keeps every membership query branch-free). Columns: `id, list_id` (FK, CASCADE), `token` (unique, indexed), `role` (`editor`|`viewer` only — a link can never mint another owner), `created_by` (FK→users), `expires_at` (nullable, unused for now but additive later), `revoked_at` (nullable), timestamps.

**`sync_events`** — `id, list_id` (FK, CASCADE), `entity_type` (`list`|`category`|`item`|`favorite_item`|`store`|`store_category_order`), `entity_id` (plain int, polymorphic — not a real FK, comment this), `op` (`create`|`update`|`delete`), `occurred_at`, `payload` (nullable json). Insert-only log, no `version` column.

Run `node ace migration:run` after writing these to regenerate `apps/api/database/schema.ts` (auto-generated — never hand-edit).

## 2. Backend authorization

No new dependency (Bouncer isn't installed and isn't needed for one access shape). New **`apps/api/app/policies/list_policy.ts`**:
- `ROLE_RANK = { viewer: 1, editor: 2, owner: 3 }`
- `roleFor(userId, listId)` → accepted `ListMember` lookup.
- `requireList(userId, listId, minRole)` → loads the list; 404 if it doesn't exist *or* user isn't a member (don't distinguish, to avoid leaking existence); 403 if role too low.
- `requireStoreRole(userId, storeId, minRole)` → union of the user's role across every list the store is attached to (`ListStore`); 404/403 analogous.

New thin `apps/api/app/exceptions/{not_found,forbidden}_exception.ts` (status 404/403 — the default handler already renders `Exception.status`).

Replace all 9 existing `ownerId` call sites with `ListPolicy` calls at these thresholds:

| Controller | Actions | Min role |
|---|---|---|
| `lists_controller.ts` | `index`, `show` | viewer |
| | `update`, `destroy` | owner |
| | `store` | n/a — but must create an `owner` `ListMember` row right after `List.create` |
| `categories_controller.ts` | `index` | viewer |
| | `store`, `update`, `destroy`, `reorder` | editor |
| `items_controller.ts` | `index`, `recent` | viewer |
| | `store`, `import`, `update`, `destroy`, `restore` | editor |
| `favorite_items_controller.ts` | `index` | viewer |
| | `store`, `update`, `destroy`, `addToList` | editor |
| `stores_controller.ts` | `index`, store-categories read (`requireList`/`requireStoreRole`) | viewer |
| | attach/create, detach, rename, `reorderCategories` | editor |

Each controller drops its local ownership-check code and imports `ListPolicy` from `#policies/list_policy`.

## 3. Backend domain: members & invites

**Models**: `list_member.ts`, `list_invite.ts`, `sync_event.ts` (extend generated schema classes, add `@belongsTo` relations); `List` gets `@hasMany(() => ListMember)` as `members`.

**Transformers**: `list_member_transformer.ts` (id/listId/userId/role/invitedAt/acceptedAt + nested user summary); `list_invite_transformer.ts` (full shape for the owner's manage view) plus a separate minimal preview transformer (listName/inviterName/role only — no token/ids) for the pre-auth endpoint.

**Validators**: `updateListMemberRoleValidator` (`role: enum(['editor','viewer'])` — can't promote/demote owner via this route), `createListInviteValidator` (same role enum).

**Controllers**:
- `list_members_controller.ts`: `index` (viewer), `update`/`destroy` (owner, both guarded against removing/demoting the last remaining owner).
- `list_invites_controller.ts`: `store`/`index`/`destroy` (revoke) — editor+ threshold.
- `invite_accept_controller.ts` (top-level, not nested): `preview` — `GET`, no auth, 404 on missing/revoked/expired; `accept` — `POST`, auth required, `ListMember.updateOrCreate` only upgrading role if the invite's role outranks any existing one.

**Routes** (`start/routes.ts`): nested `GET/PATCH/DELETE :listId/members(/:memberId)` and `GET/POST/DELETE :listId/invites(/:inviteId)` inside the existing `lists` group; a new unauthenticated `GET invites/:token` and an authenticated `POST invites/:token/accept`.

## 4. Real-time (Adonis Transmit)

Add `@adonisjs/transmit` (server) and `@adonisjs/transmit-client` (web client). New `apps/api/config/transmit.ts` with `transport: null` (local/in-process). New `apps/api/start/transmit.ts` registering `transmit.authorize('list/:id', ...)` — extract the body into a plain exported `authorizeListChannel(ctx, id)` function so it's unit-testable outside Japa's HTTP client (Transmit's own subscribe route isn't reachable through `ApiClient`).

New **`apps/api/app/events/sync_broadcaster.ts`**: a `SyncBroadcaster` interface + `TransmitSyncBroadcaster` implementation (writes a `SyncEvent` row, then `transmit.broadcast`), exposed as a swappable module-level singleton (`syncBroadcaster`, `setSyncBroadcasterForTesting`) — matches this codebase's existing DI-by-plain-import style and keeps every mutation path testable per PLAN §11. A `broadcastToStoreLists(store, input)` helper fans a Store/StoreCategoryOrder edit out to every list that store is attached to.

Wire a broadcast call into every mutating action across the 5 controllers (create/update/delete/reorder/import/restore/addToList) plus the new members/invites controllers (all broadcast a `list` update).

## 5. Frontend

- `src/lib/api/members.ts`, `src/lib/api/invites.ts` — thin typed functions following the existing `stores.ts` pattern, each with a mocked-fetch `.spec.ts`.
- `src/lib/realtime.svelte.ts` — new flat feature file (not a new `lib/stores/` directory — keeps the existing convention of `token.ts`/`selected-store.ts`-style modules for cross-cutting state). Lazily creates a `Transmit` client, SSR-safe, exposes `subscribeToList(listId, onEvent) → unsubscribe`, includes `resetRealtimeClientForTesting()` to avoid singleton leakage across specs.
- `src/lib/components/SyncToast.svelte` — dumb presentational "list was modified" toast (visible/onRefresh/onDismiss props); subscribe/unsubscribe logic stays in the page.
- `src/routes/lists/[id]/+page.svelte`: subscribe on mount, unsubscribe on destroy, show toast on any event, "Refresh" re-runs the existing load and hides the toast (no silent auto-merge — matches "no conflict resolution yet").
- New `src/routes/lists/[id]/members/+page.svelte` (role list/change/remove, gated on owner; invite-link create/copy/revoke UI).
- New `src/routes/join/[token]/+page.svelte` (+ `+page.ts` loader): preview render; logged-in → accept & open list; logged-out → login/signup links carrying `?next=/join/[token]`.
- `login`/`signup` pages: redirect to the `next` query param instead of always `/lists`, so the accept flow round-trips through auth.
- List-detail `PageHeader` actions gain a "Members" link alongside existing Stores/Categories/Favorites.

## 8. Implementation order

1. Migrations + models (with backfill) — no behavior change yet.
2. Policy layer + unit tests — still no controller changes.
3. Swap the 9 existing call sites in the 5 controllers to `ListPolicy`, add owner-membership-on-list-create, extend existing functional specs with role matrices. (Largest reviewable chunk; isolates "same behavior, now membership-based.")
4. Members/invites domain: models, transformers, validators, 3 controllers, routes, shared DTOs + rebuild, functional tests.
5. Transmit wiring: packages, config, `start/transmit.ts`, broadcaster, threading calls into every mutating action, tests.
6. Frontend API + realtime plumbing (`members.ts`, `invites.ts`, `realtime.svelte.ts`, `SyncToast.svelte`) with tests.
7. Frontend pages: members page, join page, login/signup `next` param, list-detail wiring, PageHeader link.
