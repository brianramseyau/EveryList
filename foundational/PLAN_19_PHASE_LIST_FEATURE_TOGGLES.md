# Phase 19 — Second seeded list ("Todos") + per-list feature toggles

## Context

EveryList currently seeds every new account with one "Shopping List" and assumes
shopping-oriented features (categories, shops, favorites, quantity, price) are
always wanted. The user wants the app to support non-shopping use cases (starting
with a "Todos" seeded list) without those features cluttering the UI. This requires
extending the existing single-flag precedent (`useCategories`, added for exactly
this reason) to a full set of per-list toggles, plus two new list-level ordering
settings (item sort mode, insert position for new items).

All settings are **per-list boolean/enum flags on the `lists` table** — confirmed
with the user there is no list-type/template concept in this codebase and we
should keep it that way (flags-only, matching `useCategories`). Disabling a
setting **hides UI only**; underlying data (prices, quantities, store/favorite
assignments) is preserved and reappears if re-enabled — same behavior as
`useCategories` today.

## New list settings

| Field | Type | Default | Effect |
|---|---|---|---|
| `useShops` | boolean | `true` | show/hide Shops link + per-item store field |
| `useFavorites` | boolean | `true` | show/hide Favorites link/entry points |
| `useRecent` | boolean | `true` | show/hide "Recently deleted" link |
| `useQuantity` | boolean | `true` | show/hide quantity field (add/edit form, item row, share text) |
| `usePrice` | boolean | `true` | show/hide price field + list total (add/edit form, item row, share text) |
| `itemSortOrder` | enum `'ranked' \| 'alphabetical'` | `'ranked'` | `'alphabetical'` sorts items by name within each group and disables drag-to-reorder |
| `insertPosition` | enum `'top' \| 'bottom'` | `'bottom'` | only meaningful/shown when `itemSortOrder = 'ranked'`; where a newly created item lands |
| `showStoreInList` | boolean | `true` | independent of `useShops` — when `false`, hides the per-item store-name badge in the list body only (the header store-switcher/filter menu is unaffected, since it's a functional filter, not just a label) |
| `showPriceInList` | boolean | `true` | independent of `usePrice` — when `false`, hides both per-item prices and the running total in the list view; price stays tracked/editable in the add/edit item form |

`showStoreInList`/`showPriceInList` are **display-only** toggles, distinct from
`useShops`/`usePrice` (which disable the features/fields entirely). A list can
have `useShops: true` (items still assignable to stores, store filter still
works) but `showStoreInList: false` (the per-item badge just isn't rendered).
Same relationship for price. These two only make sense when their corresponding
`useShops`/`usePrice` is `true` — hide the display toggle in settings when the
parent feature is off.

`itemSortOrder` and `useCategories` are orthogonal: category grouping stays as-is,
alphabetical sort just changes the ordering *within* each group (or the single
flat group when categories are off).

## Backend changes

1. **Migration** (`1788100000000_add_feature_toggles_to_lists_table.ts`, same
   additive-column pattern as `1786567164000_add_use_categories_to_lists_table.ts`
   — one `alterTable` per `up()`, no FK, no backfill, so no `this.defer` needed):
   adds `use_shops`, `use_favorites`, `use_recent`, `use_quantity`, `use_price`,
   `show_store_in_list`, `show_price_in_list`
   (`boolean().notNullable().defaultTo(true)`), `item_sort_order`
   (`string().notNullable().defaultTo('ranked')`), `insert_position`
   (`string().notNullable().defaultTo('bottom')`) to `lists`.

2. **`apps/api/database/schema.ts`** — auto-generated by
   `node ace migration:run`; regenerates with the 9 new columns on `ListSchema`
   once the migration above runs. Never hand-edited.

   casts for the 7 new booleans (same pattern as `useCategories` at line 21-22);
   `itemSortOrder`/`insertPosition` are plain strings, no cast needed.

4. **`apps/api/app/validators/list.ts`** — add all 9 fields as `.optional()` to
   both `createListValidator` and `updateListValidator`; enums via
   `vine.enum(['ranked', 'alphabetical'] as const).optional()` and
   `vine.enum(['top', 'bottom'] as const).optional()`. `lists_controller.ts`'s
   `update` needs no change — it already spreads validated `rest` into

   `pick(...)` array.

   defaults as the migration (so callers that omit them get today's behavior

7. **`apps/api/app/controllers/new_account_controller.ts`** — add a second
   starter config:
   ```ts
   const TODOS_LIST = { name: 'Todos', icon: 'formatListChecks', color: '<AA-safe swatch, e.g. blue-700>' } as const
   ```
   The Todos list should be a first-run tutorial and should appear **above**
   Shopping List on a brand-new user's Lists page. List order is per-user via
   `ListMember.sortOrder`, assigned ascending by `nextListMemberSortOrder`
   (`apps/api/app/services/list_member_sort.ts`) — lower value sorts first, and
   `createOwnedList` (`list_creation.ts:32-39`) calls it once per list creation,
   so **whichever `createOwnedList` call runs first gets the lower sortOrder**.
   Reorder `store()` to call `createOwnedList` for `TODOS_LIST` *before*
   `STARTER_LIST`, with `useCategories: false, useShops: false,
   useFavorites: false, useRecent: false, useQuantity: false, usePrice: false`.
   Pick the color from the existing `ColorPicker` swatches to keep the same

   doubles as category-heading text color).

   After creating the Todos list, seed a handful of onboarding items via the

   - "Tap to cross this off"
   - "Swipe left to delete, or use the pencil icon on desktop"
   - "Swipe right to edit, or tap the pencil icon on desktop"
   - "Press and hold, then drag to reorder"
   - "Add your first real to-do"

   always does `MAX(sortOrder)+1`. Add an opt-in parameter (e.g.
   `nextSortOrder(listId, { respectInsertPosition: true })`) that, when the

   Wire this through **only** on the primary item-create call site (`store()`,

## External API compatibility (OpenAPI, Home Assistant, Alexa)

The OpenAPI spec (`apps/api/config/openapi.ts`, generated by
`apps/api/app/services/openapi/*` from the live routes/Vine validators/transformers,
regenerated automatically on every build via `apps/api/hooks/openapi_build.ts`) is
**not hand-maintained** — adding the fields to `list.ts`'s validators and the
transformer's `pick(...)` array updates the generated spec automatically; no
separate doc-sync step is needed.

Both external integrations hit the same versioned `/api/v1/...` surface as the
web app, via scoped Personal Access Tokens — there's no frozen/legacy API surface
for them:
- **Alexa skill** — in-repo (`alexa/`, `alexa_controller.ts` etc.), works off
  intents (add/remove/complete/read/set-default), not a strict hard-coded schema.
- **Home Assistant** — the HACS integration is a sibling repo at
  `../EveryList-hass` (`custom_components/everylist/`), inspected directly. Its
  `EveryListList.from_json` (`api.py:81-82`) only ever reads `id, name, icon` off
  the List response via explicit key extraction (not strict/`extra=forbid`
  parsing) — any other field, existing or new, is silently ignored. It never
  sends a list-create/list-update request at all (no such method exists in
  `api.py`/`config_flow.py`); its writes are item-level only (`create_item`,
  `update_item`, `move_item`), each sending a small explicit field set.
  **Confirmed: adding these 9 fields cannot break this integration.**

All 9 new fields are **additive and optional** with server-side defaults that
reproduce today's behavior exactly (`insertPosition` defaults to `'bottom'`,
matching the previous always-append `nextSortOrder` behavior, so no existing
list changed behavior unless a user explicitly opts into "insert at top" via
settings). Vine's validators only validate fields they declare and silently
ignore unrecognized/missing keys — so requests from HA/Alexa that don't send
these new fields kept working, and responses gained new keys those clients
simply don't look at. Both integrations were confirmed safe against this change.
